# Data Model

Data structure of the CrossFit training log application. Storage: MongoDB. Backend: Python, FastAPI, Pydantic v2. Authentication: Keycloak (no users collection; the user is identified by the access token).

> This document is the contract between backend and frontend. The OpenAPI spec is generated from the Pydantic models in CI. If this document and the models disagree, fix the document.

## 1. Principles

1. **Workouts are logged only.** A training document stores what was performed, not a plan. Statistics are computed from these documents.
2. **Exercise type is the single source of truth for the set structure.** The `modality` of an exercise (`G`, `W`, `M`) selects the Pydantic model of a set. There is no universal set with all metrics.
3. **The client sends ids, not exercises.** A set carries `type` and `exercise_id`. The backend loads exercises, checks that `exercise.modality == set.type`, and adds a snapshot.
4. **Snapshot over lookup.** Saved sets contain a copy of the exercise data needed for reading and analytics. History does not change when an exercise is renamed, and aggregations need no `$lookup`.
5. **Complexes are templates.** A complex is expanded into plain sets when it is added to a workout. Saved workouts contain only regular sets with a `complex` marker.
6. **One unit system, no unit suffixes.** Field names carry no units (`time`, `distance`, `weight`). The units are fixed by this document (section 2) and repeated in the field descriptions of the Pydantic models, so they appear in the OpenAPI spec. Conversions are done on the client.
7. **Derived values are not stored.** Pace, volume and similar values are computed.

## 2. Conventions

| Value        | Field names                    | Type    | Unit / rule                      |
|--------------|--------------------------------|---------|----------------------------------|
| Time         | `time`, `time_cap`             | `int`   | seconds                          |
| Distance     | `distance`                     | `int`   | meters                           |
| Weight       | `weight`                       | `float` | kilograms (52.5 is valid)        |
| RPE          | `rpe`                          | `float` | 1 to 10                          |
| Calories     | `calories`                     | `int`   | kcal                             |
| Training date| `date`                         | `date`  | `YYYY-MM-DD`, no time, no time zone |
| Timestamps   | `created_at`, `updated_at`     | `datetime` | UTC, BSON `Date`              |
| User id      | `user_id`, `created_by`        | `UUID`  | Keycloak `sub`                   |
| Document ids | `_id`, `*_id`                  | `ObjectId` | `str` in the API              |

Naming: `snake_case` everywhere. Enum-like values are lowercase `snake_case`, except modality codes `G`, `W`, `M`.

**UUID storage.** User ids are stored as BSON UUID (binary subtype 4). Configure the MongoDB client with `uuidRepresentation="standard"`. In the API they are strings.

**Date storage.** `date` is stored as an ISO string `YYYY-MM-DD`. Such strings sort and compare correctly, so range queries (`$gte`, `$lt`) work without time zone handling.

## 3. Collections

| Collection   | Purpose                                              |
|--------------|------------------------------------------------------|
| `exercises`  | Global exercise catalog                              |
| `complexes`  | Complex templates                                    |
| `trainings`  | Workout logs                                         |

There is no `users` collection.

## 4. Exercises

### 4.1 Document

```json
{
  "_id": "665f1a2b3c4d5e6f7a8b9c03",
  "slug": "front-squat",
  "name": "Front squat",
  "search_terms": ["front squat", "front", "squat"],
  "modality": "W",
  "movement_pattern": "squat",
  "muscle_groups": ["quads", "glutes", "core"],
  "equipment": ["barbell"],
  "is_archived": false
}
```

### 4.2 Fields

| Field              | Type         | Notes                                                                    |
|--------------------|--------------|--------------------------------------------------------------------------|
| `slug`             | `str`        | Unique, lowercase, `a-z0-9-`                                             |
| `name`             | `str`        | Display name                                                             |
| `search_terms`     | `list[str]`  | Generated by the backend: lowercase full name plus each word of the name |
| `modality`         | `G | W | M`  | Defines the set model. Immutable once the exercise is used in a log      |
| `movement_pattern` | `str`        | `squat`, `hinge`, `push`, `pull`, `carry`, `core`, `locomotion`, `other` |
| `muscle_groups`    | `list[str]`  | Used for statistics                                                      |
| `equipment`        | `list[str]`  | `barbell`, `dumbbell`, `kettlebell`, `bodyweight`, `rower`, ...          |
| `is_archived`      | `bool`       | Soft delete                                                              |

`modality` classifies the exercise and selects the set structure. `movement_pattern`, `muscle_groups` and `equipment` are orthogonal categorization used for statistics and do not affect the set structure.

Not included for now (can be added later without breaking existing data): aliases, tags, unilateral flag, custom (user-owned) exercises.

### 4.3 Modalities

| Code | Name       | Typical exercises                        | Set model       |
|------|------------|------------------------------------------|-----------------|
| `G`  | Gymnastics | pull-ups, push-ups, burpees, toes-to-bar | `GymSetIn`      |
| `W`  | Weight     | deadlift, snatch, kettlebell swing       | `WeightSetIn`   |
| `M`  | Cardio     | run, row, bike, ski                      | `CardioSetIn`   |

Exercises that do not fit are solved by optional fields (for example weighted pull-ups are `G` with `weight`). If a real need for a fourth structure appears, add a new model to the union.

### 4.4 Autocomplete

The frontend sends the typed prefix to `GET /exercises/search?q=`. The backend uses a lowercase anchored regex on `search_terms` and returns up to 10 matches including `id` and `modality`, so the UI can render the correct set fields. Because `search_terms` contains each word of the name, typing `squ` finds both `Front squat` and `Back squat`.

```python
db.exercises.find({
    "is_archived": False,
    "search_terms": {"$regex": f"^{re.escape(q.lower())}"},
}).limit(10)
```

### 4.5 Rules

- The catalog is global. Create, update and archive operations are restricted to a privileged role; all users can read.
- Exercises are never hard-deleted. `DELETE` sets `is_archived = true`. Archived exercises do not appear in search but stay valid for existing logs.
- `modality` cannot be changed once the exercise is referenced by any training.

## 5. Sets

### 5.1 Input (from the frontend)

A set is a flat object. `type` is the discriminator.

```json
{ "type": "W", "exercise_id": "665f1a2b3c4d5e6f7a8b9c03", "reps": 5, "weight": 110, "rpe": 8 }
```

| Field         | `G` Gymnastics | `W` Weight | `M` Cardio |
|---------------|:--------------:|:----------:|:----------:|
| `exercise_id` | required       | required   | required   |
| `reps`        | required       | required   | not used   |
| `weight`      | optional       | optional   | not used   |
| `rpe`         | not used       | optional   | not used   |
| `time`        | optional       | optional   | optional*  |
| `calories`    | not used       | not used   | optional*  |
| `distance`    | not used       | not used   | optional*  |
| `comment`     | optional       | optional   | optional   |

\* Cardio requires at least one of `time`, `calories`, `distance`.

### 5.2 Stored (in the database)

The stored set equals the input set plus the exercise snapshot and an optional complex marker:

```json
{
  "type": "W",
  "exercise_id": "665f1a2b3c4d5e6f7a8b9c03",
  "exercise": {
    "name": "Front squat",
    "movement_pattern": "squat",
    "muscle_groups": ["quads", "glutes", "core"],
    "equipment": ["barbell"]
  },
  "reps": 5,
  "weight": 80,
  "rpe": 8,
  "complex": null
}
```

In MongoDB `exercise_id` is an `ObjectId`.

## 6. Sections

A training consists of an ordered list of sections. All sections have the same structure; `kind` only labels the purpose.

| Field        | Type                   | Notes                                                       |
|--------------|------------------------|-------------------------------------------------------------|
| `kind`       | enum                   | `warm_up`, `lifting`, `metcon`, `accessory`, `cool_down`    |
| `format`     | enum                   | `standard`, `amrap`, `emom`, `for_time`, `tabata`           |
| `rounds`     | `int | null`           | Required for `for_time`                                     |
| `time_cap`   | `int | null`           | Seconds. Required for `amrap` and `emom`                    |
| `items`      | list of sets / complex references | At least one item                                |
| `comment`    | `str | null`           |                                                             |

Sections are an array (not fixed keys), so a training can contain several sections of the same kind and the order is preserved. Aggregations use `$unwind` and group by `kind`.

Example metcon: AMRAP 12 minutes of 10 pull-ups, 15 kettlebell swings, 200 m run.

```json
{
  "kind": "metcon",
  "format": "amrap",
  "time_cap": 720,
  "items": [
    { "type": "G", "exercise_id": "665f1a2b3c4d5e6f7a8b9c02", "reps": 10 },
    { "type": "W", "exercise_id": "665f1a2b3c4d5e6f7a8b9c04", "reps": 15, "weight": 24 },
    { "type": "M", "exercise_id": "665f1a2b3c4d5e6f7a8b9c01", "distance": 200 }
  ],
  "comment": "Scaled"
}
```

## 7. Complexes

A complex is a reusable sequence of sets (for example a barbell complex).

### 7.1 Template (`complexes` collection)

```json
{
  "_id": "665f...",
  "slug": "barbell-complex-a",
  "name": "Barbell complex A",
  "tags": ["barbell", "olympic"],
  "format": "standard",
  "rounds": null,
  "time_cap": null,
  "items": [
    { "type": "W", "exercise_id": "...", "reps": 1 },
    { "type": "W", "exercise_id": "...", "reps": 2 },
    { "type": "W", "exercise_id": "...", "reps": 1 }
  ],
  "owner_id": null,
  "is_archived": false
}
```

`items` use the same set models as sections. **Nested complexes are forbidden.**

### 7.2 Reference in a training

A section item can be a complex reference:

```json
{ "type": "complex", "complex_id": "665f...", "rounds": 3, "weight": 60, "rpe": 7 }
```

| Field        | Notes                                                                              |
|--------------|------------------------------------------------------------------------------------|
| `complex_id` | Template id                                                                        |
| `rounds`     | How many times the complex was performed (default 1)                               |
| `weight`     | Shared weight, applied to `W` and `G` components that have no own weight           |
| `rpe`        | Applied to `W` components                                                          |

### 7.3 Expansion

Before saving, the backend replaces every reference with plain sets, repeated `rounds` times. Each expanded set gets a marker:

```json
{
  "type": "W", "exercise_id": "...", "reps": 2, "weight": 60, "rpe": 7,
  "exercise": { "name": "Front squat", "movement_pattern": "squat" },
  "complex": { "id": "665f...", "name": "Barbell complex A", "round": 1 }
}
```

Consequences:

- Statistics treat these sets like any other set, with no special aggregation.
- Later changes to the template do not alter saved workouts.
- The UI groups sets by `complex.id` + `round`.
- To change `rounds` or the shared weight, the frontend edits the reference and resends the whole training; the backend rebuilds the document. Expanded sets are never patched by hand.

## 8. Training (workout log)

### 8.1 Document

```json
{
  "_id": "665f...",
  "schema_version": 1,
  "user_id": "3f1c2d9e-8a4b-4c6e-9f10-1a2b3c4d5e6f",
  "created_by": "3f1c2d9e-8a4b-4c6e-9f10-1a2b3c4d5e6f",
  "title": "Monday: front squat + metcon",
  "date": "2026-10-19",
  "comment": null,
  "sections": [ ... ],
  "created_at": "2026-10-19T19:02:11Z",
  "updated_at": "2026-10-19T19:02:11Z"
}
```

| Field            | Notes                                                                                    |
|------------------|------------------------------------------------------------------------------------------|
| `schema_version` | Integer, increment on breaking structure changes. Simplifies migrations                  |
| `user_id`        | Whose workout it is (Keycloak `sub`, UUID)                                               |
| `created_by`     | Who created it (UUID). Equals `user_id` now; differs when a trainer logs for a trainee   |
| `date`           | Day of the workout, date only. Used by calendar and list views                           |
| `created_at`, `updated_at` | Set by the backend                                                             |

The training has no time-of-day timestamp. The `date` field is the only temporal attribute of a workout, and it is required for calendar placement and statistics by week and month.

### 8.2 Access

- A user reads and writes only trainings with `user_id == token.sub`.
- Planned: role `trainer` can access trainings of own trainees; role `trainee` cannot create or edit workouts structure by themselves. The `user_id` / `created_by` split already supports this without a data migration.

## 9. Pydantic models

### 9.1 Common types

```python
from datetime import date, datetime
from typing import Annotated, Literal
from uuid import UUID

from bson import ObjectId
from pydantic import AfterValidator, BaseModel, Field, model_validator


def _check_object_id(v: str) -> str:
    if not ObjectId.is_valid(v):
        raise ValueError("Invalid ObjectId")
    return v

ObjectIdStr = Annotated[str, AfterValidator(_check_object_id)]
Modality = Literal["G", "W", "M"]
```

### 9.2 Exercises

```python
MovementPattern = Literal[
    "squat", "hinge", "push", "pull", "carry", "core", "locomotion", "other"
]


class ExerciseIn(BaseModel):
    slug: str = Field(pattern=r"^[a-z0-9-]+$")
    name: str = Field(min_length=1, max_length=120)
    modality: Modality
    movement_pattern: MovementPattern | None = None
    muscle_groups: list[str] = []
    equipment: list[str] = []


class ExerciseDB(ExerciseIn):
    search_terms: list[str]          # generated by the backend
    is_archived: bool = False
```

`search_terms` generation:

```python
def build_search_terms(name: str) -> list[str]:
    n = name.lower().strip()
    return list(dict.fromkeys([n, *n.split()]))
```

### 9.3 Sets (input)

```python
class SetBase(BaseModel):
    exercise_id: ObjectIdStr
    comment: str | None = None


class GymSetIn(SetBase):
    type: Literal["G"]
    reps: int = Field(gt=0)
    time: int | None = Field(None, gt=0, description="seconds")
    weight: float | None = Field(None, gt=0, description="kilograms")


class WeightSetIn(SetBase):
    type: Literal["W"]
    reps: int = Field(gt=0)
    weight: float | None = Field(None, gt=0, description="kilograms")
    rpe: float | None = Field(None, ge=1, le=10)
    time: int | None = Field(None, gt=0, description="seconds")


class CardioSetIn(SetBase):
    type: Literal["M"]
    time: int | None = Field(None, gt=0, description="seconds")
    calories: int | None = Field(None, gt=0, description="kcal")
    distance: int | None = Field(None, gt=0, description="meters")

    @model_validator(mode="after")
    def at_least_one_metric(self):
        if not (self.time or self.calories or self.distance):
            raise ValueError("At least one of time, calories, distance is required")
        return self


SetIn = Annotated[
    GymSetIn | WeightSetIn | CardioSetIn,
    Field(discriminator="type"),
]
```

### 9.3.1 Complex reference

```python
class ComplexRefIn(BaseModel):
    type: Literal["complex"]
    complex_id: ObjectIdStr
    rounds: int = Field(1, gt=0)
    weight: float | None = Field(None, gt=0, description="kilograms")
    rpe: float | None = Field(None, ge=1, le=10)


SectionItemIn = Annotated[
    GymSetIn | WeightSetIn | CardioSetIn | ComplexRefIn,
    Field(discriminator="type"),
]
```

### 9.4 Sections and training (input)

```python
SectionKind = Literal["warm_up", "lifting", "metcon", "accessory", "cool_down"]
SectionFormat = Literal["standard", "amrap", "emom", "for_time", "tabata"]


class SectionIn(BaseModel):
    kind: SectionKind
    format: SectionFormat = "standard"
    rounds: int | None = Field(None, gt=0)
    time_cap: int | None = Field(None, gt=0, description="seconds")
    items: list[SectionItemIn] = Field(min_length=1)
    comment: str | None = None

    @model_validator(mode="after")
    def check_format(self):
        if self.format in ("amrap", "emom") and not self.time_cap:
            raise ValueError(f"{self.format} requires time_cap")
        if self.format == "for_time" and not self.rounds:
            raise ValueError("for_time requires rounds")
        return self


class TrainingIn(BaseModel):
    title: str = Field(min_length=1, max_length=120)
    date: date
    comment: str | None = None
    sections: list[SectionIn] = Field(min_length=1)

    def exercise_ids(self) -> set[str]:
        return {
            i.exercise_id
            for s in self.sections
            for i in s.items
            if i.type != "complex"
        }

    def complex_ids(self) -> set[str]:
        return {
            i.complex_id
            for s in self.sections
            for i in s.items
            if i.type == "complex"
        }
```

### 9.5 Stored models

Stored models extend the input models with the snapshot and the complex marker. References are already expanded, so `items` contain only sets.

```python
class ExerciseSnapshot(BaseModel):
    name: str
    movement_pattern: str | None = None
    muscle_groups: list[str] = []
    equipment: list[str] = []


class ComplexMarker(BaseModel):
    id: ObjectIdStr
    name: str
    round: int = Field(ge=1)


class _DBMixin(BaseModel):
    exercise: ExerciseSnapshot
    complex: ComplexMarker | None = None


class GymSetDB(GymSetIn, _DBMixin): ...
class WeightSetDB(WeightSetIn, _DBMixin): ...
class CardioSetDB(CardioSetIn, _DBMixin): ...

SetDB = Annotated[
    GymSetDB | WeightSetDB | CardioSetDB,
    Field(discriminator="type"),
]


class SectionDB(SectionIn):
    items: list[SetDB]


class TrainingDB(TrainingIn):
    schema_version: int = 1
    user_id: UUID
    created_by: UUID
    created_at: datetime
    updated_at: datetime
    sections: list[SectionDB]
```

### 9.6 Complex template

```python
class ComplexTemplate(BaseModel):

    slug: str
    tags: list[str] = []
    format: SectionFormat = "standard"
    rounds: int | None = Field(None, gt=0)
    time_cap: int | None = Field(None, gt=0, description="seconds")
```

## 10. Save flow (`build_training_doc`)

1. Validate the payload with `TrainingIn` (discriminated unions, per-type fields, section format rules).
2. Collect `exercise_ids` and `complex_ids`.
3. Load all complexes in one query; load all exercises needed (own ids plus those inside templates) in one query.
4. Fail with `404` if any exercise or complex is missing or not available to the user.
5. Expand complex references into plain sets with the `complex` marker (apply shared `weight` and `rpe` where a component has none).
6. For every set check `exercise.modality == set.type`; otherwise `422`.
7. Add `exercise` snapshot to each set.
8. Set `user_id` and `created_by` (UUID from the token), timestamps, `schema_version`.
9. Validate the result with `TrainingDB`, convert id strings to `ObjectId`, and insert or replace.

The number of database queries does not depend on the number of sets.

## 12. Statistics (preview)

Statistics are computed from `trainings` by aggregation. Because every set holds its exercise snapshot, no joins are needed.

Weekly tonnage by movement pattern:

```python
[
  {"$match": {"user_id": user_id, "date": {"$gte": start, "$lt": end}}},  # ISO date strings
  {"$unwind": "$sections"},
  {"$unwind": "$sections.items"},
  {"$match": {"sections.items.type": "W", "sections.items.weight": {"$ne": None}}},
  {"$group": {
      "_id": {
          "week": {"$isoWeek": {"$dateFromString": {"dateString": "$date"}}},
          "pattern": "$sections.items.exercise.movement_pattern",
      },
      "tonnage": {"$sum": {"$multiply": ["$sections.items.reps", "$sections.items.weight"]}},
      "sets": {"$sum": 1},
  }},
  {"$sort": {"_id.week": 1}},
]
```

Pace (`time / distance`) and other derived values are computed on read. One-rep-max estimation is out of scope.

## 13. Validation rules summary

| Rule                                                                  | Where                  | Error |
|-----------------------------------------------------------------------|------------------------|-------|
| `type` is one of `G`, `W`, `M`, `complex`                             | Pydantic discriminator | 422   |
| Numeric ranges (`reps > 0`, `rpe` 1 to 10, ...)                       | Pydantic               | 422   |
| Cardio has at least one metric                                        | Pydantic               | 422   |
| `amrap` / `emom` require `time_cap`; `for_time` requires `rounds`     | Pydantic               | 422   |
| Exercise and complex ids exist and are available to the user          | `build_training_doc`   | 404   |
| `exercise.modality == set.type`                                       | `build_training_doc`   | 422   |
| No nested complexes                                                   | Complex template model | 422   |
| `modality` unchanged after the exercise is used                       | Exercises API          | 409   |
| User accesses only own trainings                                      | Endpoints              | 403   |

## 14. Evolution

- Breaking changes to the training structure increment `schema_version`; migrations are scripts run on deploy.
- Adding an optional field to a set model is not a breaking change. The same holds for adding optional exercise fields such as aliases or tags.
- A new set structure (a fourth modality) means: new `Literal` value, new `*SetIn` and `*SetDB` models, extension of both unions, and a new `modality` value in the exercise model.
- Workout plans (prescriptions) are out of scope. If they are added later, introduce a separate collection and reuse `SetIn` models, instead of extending `trainings`.
